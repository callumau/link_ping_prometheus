# Phase-1 review — CONCURRENCY THREAD-PROFILE & HAZARD LEDGER (read-only)

Repo: `/home/mish/Projects/tcp_ping_prometheus`, branch `audit/round2-v0.8`.
Files inspected in full: `main.go`, `logsink.go`, `logacl_windows.go`, `internal/prober/client.go`, `internal/prober/server.go`, `internal/prober/mtu.go`, `internal/prober/status.go`, `internal/prober/adaptive.go`.

## Review

- **Correct:** The codebase's concurrency is deliberately and consistently confined. (a) The hot-path shared state is channel- or atomic-guarded, not mute-guarded: `respCh`/`done`/`readerDone` (client.go:1015–1030), `state.pathMTU`/`state.rtoNs` as `atomic.Int64` with the exact two-goroutine rationale in comments (client.go:814, 820), `freed` as a cap-1 channel with a *blocking* send and documented rationale (client.go:287, 301–312). (b) Where a mutex *is* used it is named in a comment stating the invariant: `stragglersMu` ("Only the supervisor goroutine mutates `live`"… client.go:279–282), `dynMu` + "Caller must hold dynMu" on `sweepExpired` (server.go:509–519), `StatusRegistry.mu` with the load-bearing straggler-flag merge pinned by comment (status.go:70–77). (c) Two deliberate no-lock single-owner structures are explicitly documented as such: `echoDupGuard` ("Used only from the single echo-loop goroutine… no locking", server.go:266–276) and the RunClient supervisor's `live`/`desired` maps. (d) Every join has a bound: reader join ≤ `mtuReadArm` (client.go:1336), sweep joined via `sweepDone` inside `probeTarget`'s defer (client.go:857–866), dyn sweeper joined via `dynStop`/`dynDone` (server.go:567–590), metrics drain bounded by `shutdownJoinGrace` (main.go:62) and `svcStopDeadline` (main.go:754). (e) No `os.Exit` / silent-nil-error panic paths violate the failure-visibility rules; `ServePacketConn` returns the recovered panic as an error (server.go:428–434).
- **Finding (P2, report-only):** `drainLive` (client.go:495–520) shares **one** `time.Timer` across the sequential `select` loop over straggler `done` channels: once the timer fires for the first straggler, its channel stays ready, so every *subsequent* straggler's wait is cut to zero. The comment says "one final bounded wait" so the behavior is arguably intentional (a single total bound), but it is worth a one-line comment so a refactor doesn't "fix" it into N×N per-straggler waits during a wedged shutdown. No action required for this audit.
- **Finding (P2, report-only):** the `program.Stop` drain goroutine (main.go:762–766) leaks permanently past `svcStopDeadline` if a probe loop never exits; acceptable because the process exits either way (SCM path and foreground path both terminate), but it is an unbounded goroutine in test runs — noted so a future leak-check (e.g. `goleak`) doesn't chase a phantom.
- **Merge verdict: OK with notes** (read-only coverage lane; no edits were made to any file).
